# dsh-filex：Office/PDF/EPUB/ODF 文件内容提取插件

## 计划概述

- **目标**：实现一个 dsh 插件 `dsh-filex`，向 LLM 暴露 6 个面向模型的工具（`extract_pdf` / `extract_word` / `extract_ppt` / `extract_excel` / `extract_epub` / `extract_odf`），使用纯 WASM / 纯 JS 库在端侧提取 office、pdf（非扫描件）、epub、odf 文档内容，默认输出 Markdown。
- **范围**：包含 `scratch-plugin/` 下的所有源码、依赖声明、patch 入口文件；包含 1 份 README（启动/挂载步骤）；不包含 dsh 主仓库的任何改动；不包含端到端/单元测试（遵循"未明确要求则不写测试"红线）。
- **预期成果**：
  1. 6 个工具可在 dsh web UI 中被 LLM 正常调用并返回 Markdown；
  2. office 工具支持 doc/docx/ppt/pptx/xls/xlsx 六种格式；odf 工具支持 odt/odp/ods/odg 四种格式；epub 工具支持 .epub；
  3. PDF 工具对扫描件给出明确 `{pdf_type, markdown:null, warning}` 结果，不抛异常；
  4. 文件路径支持绝对路径与 `working_directory` 相对路径，并防 path traversal；
  5. 所有 Markdown 输出通过统一的 `textToMarkdown(htmlString)` 适配器生成，避免各分支风格漂移。
- **预计工时**：1.5 个工作日（首次实现 + 调试 WASM 加载 + epub/odf 适配 + 一次启动验证）。

## 需求背景

- **原始需求**：做一个 dsh 插件，实现提取 office、pdf（非扫描件）等格式文件内容的功能。后续追加：epub、odf 两种格式。
- **澄清记录**（用户已通过选择题确认）：
  | 维度 | 决定 |
  | --- | --- |
  | 工具粒度 | pdf / word / ppt / excel / epub / odf 共 6 类；扫描件判断作为 pdf 提取工具的内部库；pdf 提取工具只支持非扫描件 |
  | 输入参数 | 本地文件绝对路径 `file_path` + 用户工作空间 `working_directory` |
  | 输出格式 | Markdown（office/pdf 用原生 toMarkdown；epub/odf 走统一适配器生成） |
  | 扫描件策略 | 返回 `{pdf_type, markdown:null, warning}`（领域级"不理想但合法"的结果，由 LLM 决定后续动作） |
  | ODF 实现 | 用 `odf.js`（来自 GitHub org `odf.js/odf.js`，npm 包名 `odf.js`），支持 .odt/.odp/.ods/.odg；输出走 DocumentTree → 自写 markdown 适配器 |
  | EPUB 实现 | 不用 epubjs；用 `jszip` 解压 + 解析 `content.opf` + `ncx/toc` + 解析 `OEBPS/*.xhtml`；输出走 `htmlparser2` 提取纯文本 + 自写 markdown 适配器 |
- **业务价值**：让 dsh 内的 agent 能直接读取 office / pdf / epub / odf 文档原文进行摘要、问答、RAG 等下游任务；纯 WASM / 纯 JS 端侧处理，文件不出本机，符合 AGENTS.md 的"最小依赖 / 离线"原则。
- **成功标准**：
  - 启动 dsh web 应用，`Settings → Plugins` 中插件状态为 Enabled；
  - LLM 调用 `extract_word { file_path, working_directory }` 能拿到 docx 的 Markdown；
  - LLM 调用 `extract_pdf` 处理扫描件 PDF 时，结果包含 `pdf_type` 与 `warning`，不抛异常；
  - LLM 调用 `extract_epub { file_path, working_directory }` 能拿到 epub 章节顺序的 Markdown；
  - LLM 调用 `extract_odf { file_path, working_directory }` 能拿到 .odt/.ods/.odp/.odg 的 Markdown 或 Markdown 表格。

## 设计原则遵循

- **dsh 插件三步法**：插件源码 + cordis.yml patch + `pnpm dsh web --patch` 启动验证（AGENTS.md §三步创建插件）。
- **依赖声明显式**：`export const inject = ['tools']`（guide.md §5、§14）。
- **绝对路径 patch**：`scratch-plugin/cordis.yml` 中 `name` 必须使用绝对路径（AGENTS.md §关键约束）。
- **自动清理优先**：工具通过 `ctx.tools.register` 注册，框架自动 dispose；WASM 文档在每次 `execute` 内 `try/finally doc.free()`，不依赖外部 `ctx.effect`。
- **函数形式 + 仅具名导出**：使用函数形式插件（guide.md §4.1），**不**使用 `export default`（搜索结果提示：混入形式会让 loader 静默丢失 `inject`）。
- **`additionalProperties: false`**：所有对象类型的 `output.schema` / `parameters` 都加上，避免注册失败。
- **基础设施错误抛异常，领域级错误用规范值**（搜索结果 §核心契约）：
  - 文件不存在 / 扩展名不支持 / WASM 损坏 → `throw`；
  - 扫描件 / 分类失败 → 返回 `markdown:null + pdf_type + warning`（不抛）。

### 任务 2：实现路径解析与 WASM 懒加载工具 [P0, 1h]

#### 文件调整清单
| 操作 | 文件路径 | 说明 |
| --- | --- | --- |
| 新增 | `scratch-plugin/src/util/resolve-path.ts` | 文件路径解析与安全校验 |
| 新增 | `scratch-plugin/src/util/wasm-init.ts` | WASM 模块懒加载单例 |

#### 代码调整清单
| 操作 | 代码块/模块 | 说明 |
| --- | --- | --- |
| 新增 | `resolveSafeFilePath(workingDirectory, filePath)` | 返回绝对路径或抛错 |
| 新增 | `getOfficeWasm()` | 同步导出 office-oxide-wasm 的 `WasmDocument` |
| 新增 | `getPdfInspectorInit()` | 返回 Promise，懒初始化 `@firecrawl/pdf-inspector-wasm` |
| 新增 | `getPdfOxideInit()` | 返回 Promise，懒初始化 `pdf-oxide-wasm`（如需 init） |

#### 核心实现思路

**`resolveSafeFilePath` 逻辑步骤：**
1. 若 `workingDirectory` 不是绝对路径或不是目录 → 抛 `WorkingDirectoryInvalid`；
2. `path.resolve(workingDirectory, filePath)` 得到候选绝对路径；
3. 用 `path.relative(workingDirectory, resolved)` 判断：以 `..` 开头或等于绝对路径自身（跨盘符） → 抛 `PathOutsideWorkspace`；
4. 校验 `fs.statSync(resolved).isFile()`；否则抛 `NotAFile`；
5. 返回 `resolved`。

**`wasm-init.ts` 设计要点：**
- `office-oxide-wasm` 的 `WasmDocument` 是同步构造函数，不需要 `init()`；模块顶层 import 即完成，缓存 `Promise.resolve({ WasmDocument })` 即可；
- `pdf-oxide-wasm` 在 Node 端可能也直接可用（如有 `init` 导出则首次调用时 `await init()`），缓存 `Promise<WasmPdfDocument>`；
- `@firecrawl/pdf-inspector-wasm` 必须 `await init()`，缓存 `Promise<{ processPdf, detectPdf }>`；
- 用 `let cache: Promise<...> | null = null` 的闭包模式实现单例，并发调用安全（同一 Promise 复用）；
- `cache = (async () => { ... })()` 写法让 `await` 不阻塞后续工具定义（懒加载时机 = 首次 `execute`）。

#### 代码调整清单

| --- | --- | --- |
| 新增 | `officeFormatFromExt(ext)` | 扩展名 → `"docx"\|"xlsx"\|"pptx"\|"doc"\|"xls"\|"ppt"` |
| 新增 | `extractOffice(filePath, format)` | 读字节 → `new WasmDocument(bytes, format)` → `.toMarkdown()` → `.free()` |

#### 核心实现思路

**核心处理步骤：**
1. `const bytes = await readFile(filePath)`（用 `node:fs/promises`，监听 `exec.signal`）；
2. `const { WasmDocument } = await getOfficeWasm()`；
3. `format = officeFormatFromExt(path.extname(filePath).toLowerCase())`，未命中 → 抛 `UnsupportedOfficeExtension`；
4. `const doc = new WasmDocument(bytes, format)` 同步构造；
5. `try { return { markdown: doc.toMarkdown(), format: doc.formatName() } } finally { doc.free() }`；
6. `Symbol.dispose` 也可，但 `try/finally` 兼容性最好。

**关键数据结构：**
```ts
// types.ts
export type OfficeFormat = "docx" | "xlsx" | "pptx" | "doc" | "xls" | "ppt";

export interface OfficeExtractResult {
  markdown: string;          // toMarkdown() 输出
  format: OfficeFormat;       // doc.formatName() 实际识别结果
  format_requested: OfficeFormat; // 入参传入的格式
}
```

### 任务 4：实现 PDF 提取器（含扫描件分流） [P0, 1.5h]

#### 文件调整清单
| 操作 | 文件路径 | 说明 |
| --- | --- | --- |
| 新增 | `scratch-plugin/src/extractors/pdf.ts` | `extractPdf(filePath)` 主函数 |

#### 代码调整清单
| 操作 | 代码块/模块 | 说明 |
| --- | --- | --- |
| 新增 | `classifyPdf(bytes)` | 调用 `processPdf`（或 `detectPdf`），返回 `{pdfType, warning}` |
| 新增 | `extractPdfText(bytes)` | 调用 `pdf-oxide-wasm` 的 `toMarkdownAll()` |
| 新增 | `extractPdf(filePath)` | 编排：读文件 → 分类 → 分流 |

#### 核心实现思路

**核心处理步骤：**
1. `bytes = await readFile(filePath, { signal: exec.signal })`；
2. `inspector = await getPdfInspectorInit()` → `result = inspector.processPdf(bytes)`；
3. 基于 `result.pdfType` 分流：
   - `"TextBased"` 或 `"Mixed"`（含可抽取文本） → 调 `pdf-oxide-wasm` 拿 Markdown；
   - `"Scanned"` 或 `"ImageBased"` → 返回领域级 `{markdown:null, pdf_type, warning}`；
   - 未知类型 → 同上但 `warning` 更明确；
4. `pdf-oxide-wasm` 调用：`const doc = new WasmPdfDocument(bytes); try { return doc.toMarkdownAll() } finally { doc.free() }`；
5. 对 `Mixed` 类型，若 `processPdf` 返回 `pages_needing_ocr`（参考 firecrawl 的 doc），仍走 Markdown 抽取并在 `warning` 里提示："本页 N-M 为扫描件，未抽取文字"。

**关键数据结构：**
```ts
export type PdfType = "TextBased" | "Scanned" | "ImageBased" | "Mixed" | "Unknown";

export interface PdfExtractResult {
  markdown: string | null;   // null 表示未抽取（扫描件或分类失败）
  pdf_type: PdfType;
  warning: string | null;    // 扫描件/分类异常时给出提示
  page_count?: number;       // 抽取成功时附上总页数（来自 pdf-oxide-wasm.pageCount()）
}
```

**伪代码（核心）：**
```text
extractPdf(filePath):
    bytes = readFile(filePath)
    inspector = await init pdf-inspector
    classification = inspector.processPdf(bytes)            # { pdfType, markdown?, ... }
    if classification.pdfType in ["Scanned", "ImageBased"]:
        return { markdown: null, pdf_type: classification.pdfType,
                 warning: "PDF 为扫描件，未抽取文字。请先做 OCR 后再调用本工具。" }
    pdf = await init pdf-oxide-wasm
    doc = new WasmPdfDocument(bytes)
    try:
        markdown = doc.toMarkdownAll()
        return { markdown, pdf_type: classification.pdfType,
                 page_count: doc.pageCount(), warning: null }
    finally:
        doc.free()
    # 若 Mixed 类型且 inspector.markdown 非 null，使用 inspector.markdown 兜底（更高质量）
    if classification.markdown:
        return { markdown: classification.markdown, pdf_type: "Mixed", warning: null }
    return { markdown: null, pdf_type: "Mixed",
             warning: "PDF 为混合类型（部分页可读），本工具未抽取出可用 Markdown。" }
```

> **决策说明**：对 `Mixed` 类型，优先用 `pdf-inspector` 自带的 markdown（它对带表格/标题的文本 PDF 抽取质量更高），回退才用 `pdf-oxide-wasm`。这避免了"两者都用"带来的双倍延迟。

### 任务 5：实现 Markdown 适配器（xhtml + DocumentTree → md） [P0, 0.5h]

#### 文件调整清单
| 操作 | 文件路径 | 说明 |
| --- | --- | --- |
| 新增 | `scratch-plugin/src/util/markdown-adapter.ts` | EPUB/ODF 共用的 markdown 适配器 |
| 修改 | `scratch-plugin/src/types.ts` | 新增 `EpubExtractResult`、`OdfExtractResult` 类型 |

#### 代码调整清单
| 操作 | 代码块/模块 | 说明 |
| --- | --- | --- |
| 新增 | `xhtmlToMarkdown(xhtml: string): string` | 用 `htmlparser2` DOM 遍历，按 h1-h6 / p / ul / ol / li / table / a 映射 markdown |
| 新增 | `odfTreeToMarkdown(tree: DocumentTree, kind: OdfKind): string` | 递归遍历 DocumentTree.children，按 kind 输出 markdown |
| 新增 | `OdfKind = "wordprocessing" \| "spreadsheet" \| "presentation" \| "drawing"` | 决定遍历逻辑 |

#### 核心实现思路

**`xhtmlToMarkdown` 逻辑步骤：**
1. `const dom = htmlparser2.parseDocument(xhtml, { xmlMode: true, decodeEntities: true })`；
2. 自实现 visitor（不用第三方 markdown 库，避免引入依赖），按节点类型映射：
   - `<h1>`–`<h6>` → `#`…`######` + 文本 + `\n\n`
   - `<p>` → 文本 + `\n\n`
   - `<br>` → `\n`
   - `<strong>/<b>` → `**text**`
   - `<em>/<i>` → `*text*`
   - `<ul>/<ol>/<li>` → `- item` / `1. item`（递归处理嵌套）
   - `<table>/<tr>/<td>` → Markdown 表格（含表头检测：第一行 tr 中所有 th 或 td 作为 header）
   - `<a href>` → `[text](href)`
   - `<img>` → 跳过（无 src 网络可达性，附 caption 文本）
3. 收集文本时用 `domhandler` 的直接遍历（htmlparser2 已附带 `domutils`）；
4. 跳过 `<script>`、`<style>`、`<head>`、`<nav>` 中的 toc（epub toc 由我们另外生成）。

**`odfTreeToMarkdown` 逻辑步骤：**
1. 根据 `kind` 分发：
   - `"wordprocessing"`：遍历 `document.children` → 段落/标题/列表/表格 → markdown；
   - `"spreadsheet"`：对每个 sheet，遍历 `sheets` → 单元格 → Markdown 表格；
   - `"presentation"`：对每个 slide，遍历 shapes → 文本 → `## Slide N` + 文本；
   - `"drawing"`：类似 presentation，但只输出 readable text。
2. 通过递归 visitor 访问 DocumentTree（不用任何第三方 DOM 库）；
3. metadata（标题/作者/日期）输出为文件首部 front-matter：可选，默认不输出（避免 noise）。

**关键数据结构：**
```ts
// types.ts 新增
export interface EpubExtractResult {
  markdown: string;            // 含 TOC + 章节内容
  format: "epub";
  warning: string | null;
  chapter_count?: number;
  metadata?: { title?: string; creator?: string; language?: string };
}

export interface OdfExtractResult {
  markdown: string;            // 全文 markdown
  format: "odt" | "ods" | "odp" | "odg";
  warning: string | null;
  metadata?: { title?: string; creator?: string };
}
```

### 任务 7：实现 EPUB 提取器（jszip + htmlparser2） [P0, 1.5h]

#### 文件调整清单
| 操作 | 文件路径 | 说明 |
| --- | --- | --- |
| 新增 | `scratch-plugin/src/extractors/epub.ts` | `extractEpub(filePath)` 主函数 |

#### 代码调整清单
| 操作 | 代码块/模块 | 说明 |
| --- | --- | --- |
| 新增 | `parseContainerXml(zip)` | 读取 `META-INF/container.xml` 找 OPF 路径 |
| 新增 | `parseContentOpf(zip, opfPath)` | 读取 content.opf → manifest + spine（按 idref 顺序） |
| 新增 | `parseTocNcx(zip, opf)` | 读取 `<spine toc=>` 引用的 NCX → toc 树 |
| 新增 | `extractEpub(filePath)` | 编排：jszip → container → opf → toc → 遍历 spine → xhtmlToMarkdown |

#### 核心实现思路

**核心处理步骤：**
1. `bytes = readFile(filePath)`；
2. `zip = await JSZip.loadAsync(bytes)`（zip 实例）；
3. `container = parseContainerXml(zip)` 拿 `<rootfile full-path>` → opf 路径（通常 `OEBPS/content.opf`）；
4. `opf = parseContentOpf(zip, opfPath)`：
   - 用 `htmlparser2`（xmlMode:true）解析 content.opf；
   - 收集 `<manifest><item id=... href=...>` → `Map<id, href>`；
   - 收集 `<spine><itemref idref=...>` → `string[]`（id 顺序）；
5. `toc = parseTocNcx(zip, opf)`：若 `spine` 有 `toc` 属性，解析 NCX；否则尝试新式 nav.xhtml；失败则 TOC 留空；
6. 遍历 spine，每个 idref 查 manifest 拿 href，拼接为 `opfDir + href`；
7. `xhtmlBytes = await zip.file(entryPath).async("string")`；
8. `chapterMd = xhtmlToMarkdown(xhtmlBytes)`；
9. 拼装最终 markdown：`# ${metadata.title}\n\n## 目录\n${toc}\n\n## 正文\n${chapters.join('\n\n---\n\n')}`；
10. 提取 metadata（dc:title / dc:creator / dc:language）从 opf 的 `<metadata>`。

**关键数据结构：**
```ts
interface EpubMetadata { title?: string; creator?: string; language?: string }
interface EpubInternal {
  manifest: Map<string, string>;  // id -> href
  spine: string[];                 // idref 顺序
  toc: { label: string; href: string }[]; // 一级 + 二级
  metadata: EpubMetadata;
}
```

**伪代码（核心）：**
```text
extractEpub(filePath):
    bytes = readFile(filePath)
    zip = JSZip.loadAsync(bytes)
    opfPath = parseContainerXml(zip)                     # "OEBPS/content.opf"
    { manifest, spine, metadata } = parseContentOpf(zip, opfPath)
    toc = parseTocNcx(zip, opfPath, metadata.spineToc)
    chapters = []
    for idref in spine:
        href = manifest.get(idref)
        xhtml = zip.file(path.join(path.dirname(opfPath), href)).async("string")
        chapters.push(xhtmlToMarkdown(xhtml))
    return {
        markdown: renderEpubMarkdown(metadata, toc, chapters),
        format: "epub",
        warning: null,
        chapter_count: spine.length,
        metadata,
    }
```

> **决策说明**：不在 EPUB 提取中处理加密字体（Adobe DRM），如有需要抛 `EpubEncrypted` 错误；epubjs 方案已被用户否决。

### 任务 8：实现 ODF 提取器（odf.js） [P0, 1.5h]

#### 文件调整清单
| 操作 | 文件路径 | 说明 |
| --- | --- | --- |
| 新增 | `scratch-plugin/src/extractors/odf.ts` | `extractOdf(filePath)` 主函数 |

#### 代码调整清单
| 操作 | 代码块/模块 | 说明 |
| --- | --- | --- |
| 新增 | `odfKindFromExt(ext)` | 扩展名 → `"wordprocessing"\|"spreadsheet"\|"presentation"\|"drawing"` |
| 新增 | `extractOdf(filePath)` | 读字节 → `decodePackage` → `readOd*` → `odfTreeToMarkdown` |
| 新增 | `extractOdtText(tree)` / `extractOdsText(tree)` / `extractOdpText(tree)` / `extractOdgText(tree)` | 按 kind 走各自适配路径 |

#### 核心实现思路

**核心处理步骤：**
1. `bytes = readFile(filePath)`；
2. `pkg = decodePackage(new Uint8Array(bytes))`；
3. 按扩展名分发 reader：
   - `.odt` → `readOdt(pkg)` → tree.kind === `"wordprocessing"`
   - `.ods` → `readOds(pkg)` → tree.kind === `"spreadsheet"`
   - `.odp` → `readOdp(pkg)` → tree.kind === `"presentation"`
   - `.odg` → `readOdg(pkg)` → tree.kind === `"drawing"`
4. 调对应 `extractOd*Text(tree)`；
5. 拼装返回结构 `{ markdown, format, warning: null, metadata: tree.metadata }`。

**`extractOdtText(tree)` 伪代码：**
```text
walk document.children recursively:
    on heading(level=1..6): "#" * level + " " + text
    on paragraph: text + "\n\n"
    on list(level): indent + ("-" or "1.") + " " + text
    on table: Markdown table (header row from first row's cells)
    on section group: recurse into .children
```

**`extractOdsText(tree)` 伪代码：**
```text
for sheet in tree.sheets:
    output "## " + sheet.name + "\n\n"
    output markdown table from sheet.cells
    skip empty cells
```

**`extractOdpText(tree)` 伪代码：**
```text
for slide, i in tree.slides:
    output "## Slide " + (i+1) + "\n\n"
    for shape in slide.shapes:
        text = collectText(shape)
        if text: output "- " + text + "\n"
```

**`extractOdgText(tree)` 伪代码：**
```text
for page, i in tree.pages:
    output "## Page " + (i+1) + "\n\n"
    for shape in page.shapes: text from shape.text
    for vec in page.vectors: skip（无可读文本）
```

**关键数据结构：** 见任务 5 的 `OdfExtractResult`。

## 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| WASM 加载在 Node 端与 dsh 进程的 Node 版本不兼容 | 中 | 高 | 在 README 标注 "Node >= 22.19.0 || >= 24.0.0"；如需 pin，加 `.nvmrc`；odf.js 要求 Node >= 20 |
| `office-oxide-wasm` Node 端实际需要 `office-oxide-wasm/node` 子路径 | 中 | 中 | 在 `wasm-init.ts` 中先尝试根路径，失败再 `import("office-oxide-wasm/node")`；以 npm 包 `exports` map 为准 |
| `pdf-oxide-wasm` 不暴露 `init` 默认导出，Node 端直接 `import { WasmPdfDocument }` 即可 | 中 | 中 | 实现 `getPdfOxideInit` 时兼容两种形态（init 存在则 await，否则直接返回模块） |
| 扫描件 PDF `processPdf` 调用非常慢（>1s） | 低 | 中 | 在 `description` 中告知 LLM 调用延迟；首次调用预热（`ctx.on('ready', () => void getPdfInspectorInit())`） |
| 大文件（>50MB）内存溢出 | 低 | 高 | 不设硬限制，但在 README 标注 "建议 < 50MB"；WASM 抛 OOM 时让异常自然上抛（基础设施错误） |
| patch 文件绝对路径在 WSL 下跨 OS 拷贝失效 | 低 | 中 | README 标注"patch 中 path 必须为当前机器的绝对路径"；提供 `pnpm dsh web --patch ./scratch-plugin/cordis.yml` 让 loader 自己处理 |
| `parameters` / `output.schema` 漏写 `additionalProperties:false` | 中 | 中 | 任务 6 落地前对照 dsh 文档自检；任务评审清单列入 |
| 用户传入文件不存在 | 高 | 低 | `resolveSafeFilePath` 在 `statSync` 阶段抛 `ENOENT`，异常由工具框架自动转为 `isError` |
| `odf.js` 是 GitHub org 名，可能 npm 上有同名包被占用 | 中 | 中 | 在 README 锁定安装来源为 `odf.js@<version>`；若包不存在改用 `odf-kit`（API 不兼容需要适配） |
| EPUB 加密（Adobe DRM / LCP）文件 | 中 | 中 | 抛 `EpubEncrypted` 错误；description 中说明未支持加密 epub |
| ODF 文件含图表、公式、嵌入对象时 markdown 简化丢失信息 | 高 | 低 | description 中明确"以纯文本与表格为主，复杂元素保留为占位说明"；不试图还原完整版式 |
| `htmlparser2` 解析 XHTML 时遇到未命名命名空间（epub 中常见） | 中 | 低 | 解析时 `recognizeSelfClosing: true`、`xmlMode: true`；遇到解析错误降级为纯文本（去标签） |
